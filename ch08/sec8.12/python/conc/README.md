
## Property-Based Testing for Concurrent Code

Concurrency bugs are among the hardest to find with traditional testing.
A race condition may surface only under a specific thread schedule — one
that a hand-written test case may never produce. Property-based testing
addresses this by generating a wide variety of *inputs* (thread counts,
operation sequences, transfer amounts) and checking that invariants hold
across all of them, making it far more likely to exercise the schedules
that trigger races.


### Why concurrency is hard to test

A conventional unit test executes operations in a fixed, sequential order.
It may pass thousands of times on a developer's machine and still miss a
race that only appears when the OS scheduler happens to context-switch at
exactly the wrong moment. Three properties make concurrent bugs elusive:

- *Non-determinism*: the same code can produce different outcomes on
  different runs because thread scheduling is controlled by the OS.
- *Heisenbugs*: adding instrumentation (print statements, debugger
  breakpoints) changes timing and often hides the very bug you are chasing.
- *State explosion*: the number of possible thread interleavings grows
  combinatorially with the number of threads and operations.

Property-based testing cannot enumerate all interleavings either, but it
greatly increases the probability of hitting a bad schedule by running
many independent trials with varied parameters (thread count, workload
size). When a property fails, Hypothesis shrinks the parameters to the
smallest combination that still triggers the failure.


### The examples

#### 1. Counter — read-modify-write race (`UnsafeCounter` vs. `SafeCounter`)

The classic concurrency pitfall.

```python
# Unsafe: three separate bytecodes — the GIL can be released between them
tmp = self.value      # read
self.value = tmp + 1  # write  ← another thread may have written here already
```

Two threads reading the same `value` before either writes will both
write `value + 1`, so one increment is silently lost.

`SafeCounter` wraps the same logic in a `threading.Lock`:

```python
with self._lock:
    self.value += 1   # held exclusively for the duration
```

*Property tested:*

```
SafeCounter incremented N times from M threads always equals M × N.
```

The `UnsafeCounter` version also runs in the demo (not as a Hypothesis
test, to avoid confusing the test runner), showing the race in action.

> *Note on `time.sleep(0)`* — `UnsafeCounter.increment` calls
> `time.sleep(0)` between the read and the write. This call yields the
> thread's remaining time slice to the OS, making the race window wide
> enough to trigger reliably in the demo. The race exists *without* the
> sleep (at the bytecode level), but CPython's GIL means it is rare for
> small workloads. Real code would not have the sleep; the safety concern
> is identical.


#### 2. Bank accounts — conservation under concurrent transfers

A more realistic scenario: multiple accounts, multiple concurrent
transfers, and the invariant that money is never created or destroyed.

```python
SafeBankAccount.transfer(src, dst, amount)
```

*Property tested:*

```
sum(a.balance for a in accounts) is the same before and after
any set of concurrent transfers, for any initial balances and
any sequence of (src, dst, amount) triples.
```

The implementation acquires both account locks before modifying either
balance. To prevent deadlock — two threads doing A→B and B→A
simultaneously could each hold one lock and wait forever for the other —
locks are acquired in a fixed order determined by `id()`:

```python
first, second = (src, dst) if id(src) < id(dst) else (dst, src)
with first._lock:
    with second._lock:
        ...
```

Because every thread acquires the lock with the *lower* `id` first, a
circular wait cannot form.


#### 3. Bounded queue — capacity and element preservation

A `SafeBoundedQueue` backed by a `deque` and a single mutex. Two
properties are tested:

- *Capacity invariant*: the queue size never exceeds `capacity`,
  regardless of how many producer threads are filling it concurrently.
- *Element preservation* (serial case): every item put into the queue
  can be retrieved; nothing is lost or duplicated.

The capacity property specifically requires concurrent producers to
expose races, because without a lock the `len < capacity` guard and the
`append` are two separate operations that another thread can interleave.


### Properties at a glance

| Test                              | Inputs generated by Hypothesis      | Invariant                        |
|-----------------------------------|-------------------------------------|----------------------------------|
| `test_safe_counter_property`      | thread count, increments per thread | `counter.value == n × m`         |
| `test_bank_conservation_property` | initial balances, transfer triples  | total balance unchanged          |
| `test_queue_capacity_property`    | capacity, item list                 | `queue.size() ≤ capacity` always |
| `test_queue_element_preservation` | unique item list                    | all items retrievable            |

### PBT versus traditional tests for concurrency

A traditional unit test for the counter might look like:

```python
def test_counter():
    counter = SafeCounter()
    threads = [threading.Thread(target=counter.increment) for _ in range(5)]
    for t in threads: t.start()
    for t in threads: t.join()
    assert counter.value == 5
```

This checks one specific (5 threads, 1 increment each) case and always
runs the same threads with the same workload. The property-based version:

```python
@given(st.integers(min_value=2, max_value=8),
       st.integers(min_value=5, max_value=40))
def test_safe_counter_property(n_threads, inc_per_thread):
    counter = SafeCounter()
    ...
    assert counter.value == n_threads * inc_per_thread
```

…generates 30+ combinations, including edge cases like 2 threads × 40
increments, 8 threads × 5 increments, and everything in between. If
there is a workload size where the implementation breaks (e.g., a
lock implementation that fails under high contention), Hypothesis will
find it and shrink it to the smallest triggering parameters.


### Limitations and extensions

- *True parallelism*: CPython's Global Interpreter Lock (GIL) prevents
  Python threads from running CPU-bound code in parallel on multiple
  cores. Race conditions still occur (as shown here), but they are rarer
  than in C, Java, or Go programs. For testing truly parallel code in
  Python, consider `multiprocessing` or C extensions that release the GIL.
- *Scheduling control*: PBT varies *inputs* but not the OS *scheduler*.
  For exhaustive interleaving coverage, specialised tools like
  [Lincheck](https://github.com/JetBrains/lincheck) (JVM) or
  [Coyote](https://github.com/microsoft/coyote) (.NET) inject
  controlled scheduling.
- *Stateful testing*: Hypothesis's `hypothesis.stateful` module supports
  `RuleBasedStateMachine`, which generates sequences of operations and
  checks invariants after each step — a natural fit for testing stateful
  concurrent objects.
- *Beyond locks*: the same properties apply to other synchronisation
  primitives (`threading.Semaphore`, `threading.Condition`,
  `queue.Queue`) and to `asyncio`-based concurrent code.
