## Assessment: Chapter 6 — Craftsmanship and AI Tools

### Overview

This chapter resists the usual assessment model. There is no program to run,
no output to check, no test suite to pass. The deliverables are arguments,
analyses, and documented experiences. The risk is not that students do poor
work, but that they do superficial work: producing the form of critical thinking
without the substance.

The primary tests are: can the student defend a design decision under questioning?
Can they identify a specific, non-obvious flaw in an LLM output? Can they
describe their own deskilling experience in concrete, specific terms?

**Timing:** This chapter works best assessed in two parts: a mid-chapter
formative check after the deskilling study, and a final summative assessment
after the logic audit and GPT-2 projects.

**Primary dimensions:** Reasoning and reflection (35%), Critical tool use (25%),
Process quality (25%), Technical correctness (15%).

---

### Oral Examination Questions

**Q1.** You performed the deskilling study. Describe one specific moment
in the LLM-assisted run where you accepted output you did not fully understand.
What was the output? Why did you accept it? What would you have needed to know
to evaluate it properly?
- *Follow-up:* Could you modify that piece of code confidently, without
  the LLM's help, right now? If not, what would you need to do first?

**Q2.** Walk me through one finding from your logic audit.
What was the comment? What did the code actually do?
Was the discrepancy a harmless description error or a genuine bug?
- *Follow-up:* If the comment had been written by an LLM, what property
  of LLM-generated text would explain why it was wrong in that particular way?

**Q3.** You chose design A over design B for your ambiguous-requirements exercise.
Defend that choice. What did you give up by not choosing B?
- *Follow-up:* I'm now telling you that performance is the top priority
  and code will never be extended. Does your choice change? Why?

**Q4.** In your GPT-2 failure analysis, what was the most interesting failure
you found — not the most obvious one, the most interesting one?
- *Follow-up:* That failure — was it specific to GPT-2, or would you
  expect a more capable LLM to make the same kind of mistake? Why?

**Q5.** What is the difference between code that is "clean" and code that is
"correct"? Can code be clean and wrong at the same time?
- *Follow-up:* Give me an example from the code you have read or written
  this chapter where clean and correct were in tension.

### Assessment Task: The LLM Output Critique

*Time allowed: 30 minutes. The LLM output to be critiqued is provided below.
The student should not use an LLM during this assessment.*

The following was generated by an LLM when asked:
"Explain what technical debt is and give two concrete examples."

---
*"Technical debt refers to the accumulated cost of shortcuts taken during
software development. It occurs when developers choose quick, easy solutions
over more robust approaches, creating future maintenance burdens.*

*Example 1: Using global variables instead of properly scoped local ones.
Global variables are faster to write but create hidden dependencies between
functions, making the code harder to test and modify.*

*Example 2: Not writing documentation. When code is undocumented, future
developers must reverse-engineer its intent, which takes longer than if
documentation had been written in the first place.*

*Technical debt should always be repaid as soon as possible to prevent
it from compounding over time."*

---

**Part A:** Identify two claims in this output that are not wrong but are
oversimplified to the point of being misleading. For each, write the more
accurate version.

**Part B:** The final sentence ("should always be repaid as soon as possible")
is a recommendation, not a fact. Identify the assumption it relies on.
Describe a real scenario where following this recommendation would be incorrect.

**Part C:** The output describes technical debt as resulting from "shortcuts."
What does this framing omit? Name one form of technical debt that is not the
result of a shortcut and explain why it accumulates.

**Part D:** If you were using this explanation in a class, what one correction
would you make, and why that one over others?

### Process Artifact Requirements

The LLM interaction log for this chapter is the primary assessed artifact.
It must contain, for at least three significant interactions:

1. The exact prompt used.
2. The LLM's output (or a relevant excerpt).
3. Whether the output was accepted, modified, or rejected.
4. If accepted: one step taken to verify the output.
5. If modified: what was changed and why.
6. If rejected: why, specifically — not "it was wrong" but what specific
   claim was incorrect or what the output failed to address.

A log that records only "used LLM for X" without the content of the interaction
is not assessable. The point of the log is to make the student's critical
engagement visible.

The deskilling reflection must be written no later than 48 hours after completing
both runs of the study. A reflection written weeks later from memory does not
capture the quality of the experience.

---

### Rubric Application Notes

**Reasoning and reflection (primary):** The oral Q1 and Q2 are the clearest
tests. Specific answers (naming the exact code, the exact discrepancy, the exact
moment of decision) indicate genuine engagement. Vague answers ("the LLM
sometimes made mistakes") do not.

**Critical tool use:** The quality of the LLM interaction log is the primary
evidence. A detailed log with specific corrections is worth more than a long
log with vague entries.

**Process quality:** The deskilling reflection's specificity is the test.
A genuine reflection names a concrete moment of confusion, a concrete decision
made under uncertainty, a concrete gap in understanding. A generated-looking
reflection has the right form but lacks the specificity that only direct
experience produces.

**Technical correctness (low weight):** The technical components of this
chapter (running GPT-2, the Alloy model, the TDD extension) should work.
But technical failure with clear analysis of why the failure occurred is
worth more than technical success with no analysis.
